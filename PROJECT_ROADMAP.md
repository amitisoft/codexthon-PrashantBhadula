# Personal Finance Tracker Roadmap

## 1. Project Summary

This project is a full-stack web application for personal finance management built with:

- Frontend: React + TypeScript
- Backend: ASP.NET Core Web API
- Database: PostgreSQL

The product helps users manage:

- accounts and balances
- income, expenses, and transfers
- monthly budgets
- savings goals
- recurring payments
- reports and charts

The product should feel calm, trustworthy, and easy to use, with fast data entry and clear money insights.

## 2. Assumptions

These assumptions are made so the project can move forward without blocking on small decisions:

- V1 is for single-user personal finance only, with no shared/family account permissions.
- Currency is fixed per user profile in V1. No live exchange conversion is included.
- Users manually enter transactions. Bank sync is postponed to a future release.
- Email/password authentication is used in V1.
- Recurring transactions are generated by a backend scheduled job once per day, with support for upcoming reminders in the UI.
- Dashboard and reports are optimized for monthly usage first, with custom date ranges also supported.
- Export to CSV is included in V1; PDF export is deferred to V1.1 unless time remains.
- Notifications are in-app only for V1.
- The design system will prioritize a soothing, finance-safe UI using soft neutrals, muted blue-green accents, comfortable spacing, and clear chart colors.
- The first release targets responsive web only, not native mobile apps.

Recommended principles:

- server state via TanStack Query

- consistent API layer with typed DTOs
- route guards for protected pages

```text
backend/
  PersonalFinanceTracker.Api/
    Controllers/
    Middleware/
    Extensions/
  PersonalFinanceTracker.Application/
    Interfaces/
    Services/
    DTOs/
    Validators/
    Mapping/
  PersonalFinanceTracker.Domain/
    Entities/
    Enums/
    ValueObjects/
  PersonalFinanceTracker.Infrastructure/
    Persistence/
    Repositories/
    Auth/

```

Recommended principles:

- clean separation between API, application, domain, and infrastructure
- transactional consistency for balance updates
- user-scoped data access everywhere
- centralized exception handling
- background jobs isolated from request/response flows

## 7. Data Model Enhancements

The provided schema is strong, but I recommend these additions:

- `refresh_tokens` table for secure session handling
- `transaction_tags` join table instead of storing tags as plain text if filtering by tags matters
- `account_transfers` representation or linked transfer transaction IDs for traceability
- `audit_logs` table for balance-changing operations
- `user_settings` table for base currency, locale, date format, theme preference, and notification preferences
- soft delete or archive flags where deletion could break reporting history

## 8. API Design Recommendations

### Keep from the spec

- resource-based endpoints for auth, transactions, categories, accounts, budgets, goals, recurring, and reports

### Additions recommended

- `GET /api/dashboard/summary`
- `GET /api/notifications`
- `GET /api/settings`
- `PUT /api/settings`
- `GET /api/reports/cashflow-summary`
- `POST /api/export/csv`

### API standards

- version endpoints with `/api/v1/...`
- return pagination metadata for transaction lists
- use consistent error format
- include idempotency considerations for scheduled recurring creation

## 9. Security and Reliability Plan

- hash passwords with Argon2 or BCrypt
- short-lived access tokens and rotating refresh tokens
- rate limit login and password reset endpoints
- enforce ownership checks in all queries and commands
- use DB transactions for transfers, goal contributions, and recurring generation
- seed default categories safely on user creation
- add structured logs and request correlation IDs
- daily database backup strategy in deployment

## 14. Risks and Mitigations

### Risk: balance inconsistencies

Mitigation:

- use transactional service methods
- treat transfer and goal contribution as atomic operations
- add integration tests around balance recalculation

### Risk: recurring jobs create duplicates

Mitigation:

- track execution history
- use idempotent creation logic
- lock or guard job execution window

### Risk: reports become slow with larger data

Mitigation:

- add indexes on user/date/category/account fields
- paginate transaction queries
- pre-aggregate dashboard queries if needed later

### Risk: UI becomes cluttered

Mitigation:

- maintain strict component hierarchy
- keep high-density data mainly in transactions and reports pages
- keep dashboard focused on summary and action

## 18. My Recommendation

For the best balance of speed, polish, and hackathon-friendliness:

- use React + TypeScript + Vite + Tailwind + TanStack Query on the frontend
- use ASP.NET Core 8 + EF Core + PostgreSQL on the backend
- ship CSV export in V1 and keep PDF export for later
- build the UI as calm and airy rather than dense and corporate
- focus first on transaction correctness and budget clarity, because those create the most trust in a finance app
